TableRounds Multi-speciality Platform
Architecture Upgrade Proposal
Prepared for: TableRounds
Project Investment: $2,350 USD
Estimated Timeline: 25 Days
Project Overview
The objective of this project is to transform the existing OMS-focused TableRounds platform into
a reusable multi-speciality architecture.
Instead of creating separate pages, question banks, and application logic for every speciality, the
platform will use one centralized architecture where specialties, topics, questions, subscriptions,
and related platform functionality are dynamically connected.
This approach will allow the currently planned specialties to operate within the same system
while creating a reusable foundation for future expansion.
The goal is to build the underlying system once, rather than repeatedly rebuilding similar
functionality for each new speciality.

Core Architecture
The platform will move toward the following structure:
speciality
↓
Topics
↓
Questions
↓
Difficulty
↓
Tests / Results / Statistics
Each question will be associated with its appropriate:
● speciality
● Topic
● Difficulty
When an administrator or user selects a speciality, the available topics and related content will
automatically correspond to that speciality.
This eliminates the need to build separate question-bank systems for every speciality.
Public Website Structure
The current OMS speciality page will be converted into a reusable Specialties structure.
The navigation will provide access to the available specialties, including the 20 specialties listed
above.
Rather than creating a completely separate webpage for every speciality, the same reusable
page/component structure will dynamically display the relevant speciality information.
This keeps the public website easier to maintain and makes future speciality expansion much
simpler.
Platform Integration
The reusable speciality architecture will be integrated throughout the existing TableRounds
platform.
This includes:
Question Management
● Create Questions
● Edit Questions
● Question Manager
● speciality filtering
● Topic filtering based on selected speciality
● Difficulty management
Testing System
● Create Test
● speciality-based question selection
● Topic filtering
● Test generation
● Review Test
User Platform
● Dashboard
● Question Bank
● Statistics
● Leaderboard
● speciality selection
● speciality-specific content
The existing platform infrastructure will be reused wherever possible rather than rebuilding
existing functionality.
speciality-Based Subscription Access
Subscription access will become speciality-based.
A user's account will only be able to access the specialties included in their subscription.
For example:
User with OMS Access
✓ OMS
✗ Pediatric Dentistry
✗ Orthodontics
✗ Internal Medicine
User with Multiple speciality Access
✓ OMS
✓ Pediatric Dentistry
✓ Orthodontics
The backend will enforce these permissions so users cannot retrieve restricted speciality
questions or data simply by bypassing the frontend.
The system will also be structured to support users who eventually have access to multiple
specialties.
Administration System
Administrators will be able to work across all specialties from the existing administration
environment.
The system will support:
● speciality management
● Topic management
● Question management
● speciality filtering
● Topic filtering
● Question creation
● Question editing
● User speciality access
● Subscription-related speciality permissions
Admin accounts will have access to all specialties, while regular users will only see specialties
available to their accounts.
Previous Structure vs. Current Architecture
Previous Approach
The original plan was primarily focused on adding Pediatric Dentistry to the existing OMS
system.
That approach would have required speciality-specific implementation across areas such as:
● Landing page
● Question bank
● Topics
● Questions
● Dashboard
● Statistics
● Leaderboard
● Admin
● Access control
While this would work for one additional speciality, repeating the same approach for every new
speciality would gradually increase development and maintenance costs.
Current Approach
The updated architecture treats speciality as a reusable parent category.
Instead of:
OMS System
●
Pediatric Dentistry System
●
ENT System
●
Orthodontics System
●
etc.
The platform becomes:
One TableRounds Platform
↓
speciality
↓
Topics
↓
Questions
↓
Existing Test & Learning Infrastructure
This means the same application components can serve all specialties.
The 20 specialties listed in this proposal will be configured within this architecture rather than
receiving separate duplicated systems.
Why This Architecture Is Valuable
The main value of this project is not simply adding 20 speciality names.
The primary investment is in creating the reusable infrastructure behind those specialties.
Once the architecture is established, future speciality expansion can be significantly more
efficient because the core system will already understand:
● speciality relationships
● Topic relationships
● Question relationships
● speciality-based permissions
● speciality-based subscriptions
● speciality filtering
● speciality-specific testing
● speciality-specific statistics
● speciality-specific leaderboards
This reduces the need for repeated development and makes the platform easier to maintain as
TableRounds grows.
It also provides a consistent experience across specialties instead of maintaining multiple
versions of the same application logic.

Project Investment
Total Price: $2,350 USD
This price includes the reusable multi-speciality architecture and implementation of the 20
specialties specifically listed in this proposal, along with their associated topics provided by
TableRounds.
The purpose of this pricing structure is to keep the project cost-effective while building the
foundation needed for TableRounds' future growth.
Scope Transparency
To keep the contract completely transparent, this proposal specifically covers:
20 listed specialties + their provided topics + reusable speciality architecture + integration
throughout the existing platform + testing and deployment.
The architecture itself will be designed to support future specialties, but adding additional
specialties beyond the 20 listed above can be handled separately in the future if needed.
No separate UI/UX redesign is included in this project. The existing platform design and
components will be reused wherever practical, with the necessary frontend changes made to
integrate the new speciality functionality.
Final Objective
The ultimate goal is to give TableRounds a stronger foundation for expansion.
Instead of treating every new speciality as a separate development project, the platform will
have one reusable system capable of handling speciality-specific content, questions, topics,
subscriptions, permissions, tests, statistics, and leaderboards.
This allows TableRounds to focus future investment on content and growth rather than
repeatedly rebuilding technology.
I appreciate the continued trust and long-term collaboration, and my goal is to make this
implementation as practical, scalable, and cost-effective as possible while keeping the current
beta version focused on the functionality that provides the most value.
